# Development Agent Pipeline (AI Editor Guidelines)

AIエディタ（Antigravity等）が開発タスクを実行する際、単一の思考プロセスで直接コードを書くことを禁じます。
必ず以下の「7つの専門ロール」を順次切り替え、**検討 → 点検 → 確認 → 実装 → 検証 → 記録 → リリース** の厳格なパイプラインを経由してください。

## 1. Planner（検討エージェント）
- **役割**: 要件に対し、最も「柔軟」かつ「効率的」な設計・実装方針を立案する。
- **行動指針**: 
  - 複数のアプローチを比較検討する。
  - プロジェクトの文脈（少年野球チームの運営支援）に最も適した解決策を提示する。

## 2. Reviewer（点検エージェント）
- **役割**: Plannerの立案した設計・方針を「厳密に」点検する。
- **行動指針**:
  - `RULES.md` に違反していないか粗探しを行う。
  - セキュリティリスクを監査し、問題があればPlannerに差し戻す。

## 3. Verifier（確認エージェント）
- **役割**: 設計が、ユーザーの「真の目的」を達成できるか、後述の「品質担保チェックリスト」の観点を含めて事前確認する。
- **行動指針**:
  - 仕様漏れ、エッジケースへの考慮が欠けていないかを確認する。

## 💡 品質担保チェックリスト (Quality Assurance Standards)
全エージェント、特に **Tester** と **Integrity Agent** は、以下の項目が全て満たされているかを確認すること。
　- **特に日付型（Timestamp vs String）の変換漏れを重点的に監査する。**

### ① 通信・データ整合性 (API & Data Integrity)
- 全てのPOSTエンドポイントで、`get_json(silent=True)` と `json.loads()` のフォールバックが実装されているか。
- Firestoreから取得したデータは `_format_doc` を経由し、日付が文字列（ISO形式）に変換されているか。
- Admin側で追加した新フィールドが、LIFF側やスプレッドシート側でエラーを誘発しないか。

### ② 設定・インフラ (Config & Infrastructure)
- 新機能に必要な設定値（ID/キー等）が `config.py` と `functions/.env` に反映されているか。
- 新しい秘密情報が `.gitignore` 対象ファイル以外に記述されていないか。（GitHub露出防止）
- 外部サービスへの権限付与が必要な場合、ドキュメントに明記されているか。

### ③ 状態管理・エッジケース (Edge Cases & State)
- 新規作成（ID=None）時に、そのIDを前提とした同期処理やAPI呼び出しがガードされているか。
- 必須項目が欠けた状態で「保存」した際、フロント・バック両面で安全にエラー処理されるか。

### ④ ユーザー体験・ローカライズ (UX & Localization)
- ボタン、ラベル、プレースホルダ、AIコメントが全て日本語化されているか。
- 「保存中...」「同期中...」など、非同期処理の進捗がユーザーにフィードバックされているか。
- **特にUIの変更を伴う場合、Firebase Hostingへの反映（ビルド・デプロイ）が必須であることを認識しているか。**

### ⑤ リリース整合性 (Deployment & Release Integrity)
- **フロントエンド修正時**: `admin-dashboard` または `liff-app` の修正時、対象ディレクトリで `npm run build` を実行し、`dist` が最新化されているか。
- **マルチターゲット指定**: 
  - Admin修正 -> `firebase deploy --only hosting:admin`
  - LIFF修正 -> `firebase deploy --only hosting:liff`
  - Functions修正 -> `firebase deploy --only functions`
- **実機・環境確認**: デプロイ完了後、Hosting URLにアクセスし、意図したUI変更が「実際に」反映されているかを確認したか。（ローカル確認だけで満足しないこと）

## 4. Tester（検証エージェント）
- **役割**: 実装（コーディング）完了後、その実装が正しく機能し、既存機能を破壊していないかを「必ず」検証（テスト）する。
- **行動指針**:
  - **「品質担保チェックリスト」の全項目を実機またはテストコードで確認する。**
  - 自動化されたテストコードの記述を優先し、デグレードがないことを証明する。
  - 新機能実装時は必ずテストカバレッジを確保し、既存テストスクリプトを実行してデグレード（退行）が発生していないことを証明する。
  - **「品質担保チェックリスト」**に含まれないが、必要だと考えられるテストパターンがあればテストコード確認し、問題がないことを証明する。

## 5. Integrity Agent（整合性エージェント）
- **役割**: 「管理画面（Admin）」と「ユーザー画面（LIFF）」の間のデータ構造、および「フロントエンド」と「バックエンド」の間の通信プロトコルの整合性を厳格に維持する。
- **行動指針**:
  - フロントエンドの変更がバックエンドのAPI仕様を破壊していないか、またはその逆がないかを必ず相互チェックする。
  - Firestoreのデータ型（Timestamp vs Stringなど）が、読み取り側と書き込み側の両方で一貫して扱われているかを確認する。
  - 一箇所への「便利な拡張」が、他方での「予期せぬクラッシュ」を引き起こさないよう、常にシステム全体を俯瞰して訂正を行う。

## 6. Librarian（記録エージェント）
- **役割**: 実装および検証が完了した最新の状態に基づき、`system_overview.md` や `system_details.md` 等のドキュメントを「実態と乖離させない」よう維持管理する。
- **行動指針**:
  - コード変更（データ構造、APIエンドポイント、UIフロー）が発生した際、即座に関連ドキュメントの更新内容を特定し、修正を行う。
  - 変更履歴や機能拡張が、後続の開発者やAIエージェントにとって「現在進行系の事実」として伝わるよう、正確かつ最新の情報に保つ。
  - 「実装して終わり」ではなく、ドキュメントの最新化をもって「実装完了」と定義する。

## 7. Deployer（リリースエージェント）
- **役割**: テストおよびドキュメント更新を通過した安全なコードと資料をGitHubにコミットし、Firebase環境へ確実にデプロイ（ビルド・配信）する。
- **行動指針**:
  - TesterおよびLibrarianの完了報告を確認し、全テストのパスとドキュメントの最新化をリリースの絶対条件とする。
  - 変更内容を要約し、プロジェクトの規約に沿った適切なメッセージでGitHubへ `commit` & `push` を行う。
  - Firebase CLI (`firebase deploy`) 等を用いて、検証済みのコードのみを環境へ反映させる。
  - **Hostingデプロイ時は、必ず事前に `npm run build` を経由したか、およびデプロイ後のURLで「表示の更新」を確認したかを報告に含めること。**
